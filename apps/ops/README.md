# Ops Hub (staff app)

Next.js app for BTX board members. One staff role, board member. A board member with admin rights has app_metadata.role 'admin' (owner, 2026-10-12). Design source: Figma file `byg3AToqjCajJKPI88DkOz`, page "Ops Hub (staff)".

Run it from the repo root: `npm run dev:ops` (port 3001), `npm run build:ops`, `npm run lint:ops`, `npm run typecheck:ops`.

## Modes

- **Mock mode** (no `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`): nothing is guarded, every page shows the Figma sample data, sign-in accepts any email and the code `123456` (an email starting `outsider` shows the no-access screen). `?demo=error` on Applicants and Cycle draws the "didn't load" card.
- **Live mode** (both env vars set; Vercel builds get the BTX project's public defaults from `next.config.ts`): every route needs a session whose `app_metadata.role` is `admin` or `board` (the field `public.app_role()` reads). Any other account is signed out and sees "This account doesn't have Ops Hub access. Ask a BTX admin."

## Real data and mock data

Real (live mode): Applicants list and the full application (`applications`, `application_files`, `bookings`, `interview_slots`), the two PDFs (signed 60-second links to the private `applicant-documents` bucket), and the cycle's dates (`cycles`).

Scholarships > Interviews, Scoring, Selection and Awardees (branch `ops/scholarships`): booked interviews are real (`bookings`, `interview_slots`, `applications`); pairs, scores, notes, awards and awardee steps are mock (`mock/interviews.ts`, `scores.ts`, `selection.ts`, `awardees.ts`, `staff.ts`) shaped like the draft Ops Hub tables, so going live is a loader swap in `lib/`. Their write actions (`lib/actions/`) run in memory in mock mode; the live paths call the draft tables and are not tested. `?demo=stress` and `?demo=error` draw the Figma stress and load-error states on all four pages.

Mock, all behind `mock/`: Today, the sidebar counts, scores, interviewers, stages, the interview summary, the three schedule dates `cycles` has no column for, the cycle checklist and the Scholarships chat. Swap each `mock/` module for a loader with the same shape when the Ops Hub tables exist.

## Every page (refreshed 2026-11-12)

All pages follow one contract (the rules are in `docs/DESIGN-DNA.md`): a types-only `lib/<page>-view.ts`, fixtures in `mock/<page>-view.ts`, a loader `lib/<page>-view-loader.ts`, the live loader `lib/<page>-live.ts` with its own paged reader `lib/<page>-db.ts`, pure mapping in `lib/<page>-map.ts` (unit tested), the page in `components/<page>/`, and its route in its own route group `app/(shell)/(<name>)/...` with its own `loading.tsx`. A `caps` object says which controls exist live: a control is drawn only where a real, safe write exists.

Pages: Today, Tasks, Calendar, Goals, Chat, Board members (`/people`), Finance (Budget, the budget approval screen, Fundraising, Grants), Programs (Certifications, Sponsorships, Mentorship), Outreach (Plan, Instagram, Newsletter), Scholarships (Applicants and its detail, Awardees, Cycle, Cycle settings, Interviews, Availability, Questions, Scoring, Selection), the sign-in, the "Not built yet" fallback, the 404 and the error screen.

- **Mock mode** (no Supabase env): the fixtures in `mock/*-view.ts` are the signed-off frames' values; writes change only the page's own state. `?demo=stress|empty|error|loading|failed` (and page-specific flags such as `failsend`, `longnames`, `confirm`) draw the other states; `?as=board` shows a page as a board member. Every `?demo=` flag is mock-only and ignored when Supabase env is present (each page has a loader test with `hasSupabaseEnv` mocked true). Without env the app still falls back to mock mode with a fake admin (backlog B26).
- **Live mode**: reads use the signed-in session (row-level security applies), are paged (PostgREST stops at 1,000 rows) and a failed read is a load error, never a zero. Writes are the ones listed per page in `docs/DESIGN-DNA.md` (Deviations log); nothing emails a student, posts to Instagram or sends the newsletter from a page except the existing, confirmed server actions on Interviews and Selection. Role changes go through `lib/people-actions.ts`, which needs `SUPABASE_SERVICE_ROLE_KEY` in the server's environment; so do the interview-email cron (`lib/email/interviews.ts` stops with `no-service-key` without it) and the Google Calendar sync feed. Nothing has been run against the production database.
- **Money writes are off live** (owner, 2026-10-12): Budget spending and funds, plan Approve / Decline / Undo, Fundraising "Log a gift" and Grants "Add a grant" are disabled "Coming soon" controls; mock mode shows the full flow. Sponsorships "Log a sponsorship" is live through `log_sponsorship()`.
- **Roles**: one staff role, board member. A board member with admin rights has app_metadata.role 'admin'. Everyone sees every page; only an admin sees "Give admin rights" / "Remove admin rights", Release decisions, cycle settings, the interview controls and export, and nobody sees a role control on their own row. There is no invite screen (owner, 2026-10-12): accounts are set up server side through `inviteStaff` in `lib/people-actions.ts`, which has no button.

## Google Calendar sync

Everything on the Calendar page is copied one way into the board's shared Google Calendar (info@thebtxfoundation.org) every 10 minutes. A Google Apps Script owned by info@ calls `GET /api/calendar-sync` (`app/api/calendar-sync/route.ts`), which answers only that script (a Google-signed identity token, checked in `lib/calendar-sync/verify-caller.ts`; no shared secret). The feed is built in `lib/calendar-sync/` and never includes applicant names.

The script writes through the Advanced Calendar service (switched on in its `appsscript.json`). Every synced event is privately marked when it is created, and only marked events are ever changed or deleted. Hand-made events are never touched. Edits made in Google to a synced event are put back within about 10 minutes. Each run is capped at 100 changes (40 deletions), and it refuses to empty the calendar or delete a large share of it at once; `syncNowAllowDeletes` lifts the second limit and keeps going until nothing is left to delete. A failed write marks the run as Failed, so Google emails info@. Setup, the limits, pausing (`removeTrigger`) and undoing (`deleteSyncedEvents`): [google/calendar-sync/README.md](google/calendar-sync/README.md).

## Teams interview links

BTX interviews are Microsoft Teams meetings only. Google Meet, Zoom and every other host are refused, by hand or otherwise (`isVideoUrl` in `lib/pairing-slots.ts`: https, host `teams.microsoft.com`, `teams.live.com` or `teams.cloud.microsoft`, up to 500 characters). Admins only.

- **What the button does.** In "Add the video links", **Make Teams links** first shows a confirm step with the counts ("Makes N Teams links and emails N students and their interviewers.", and how many other links it will replace). It then makes a Teams meeting for every paired interview ahead that has no link or a non-Teams link, and saves it. An interview starting within 24 hours that already has another link is never replaced automatically; it is reported as needing a hand check. After that, every paired interview ahead with a Teams link gets the video-link email (student and both interviewers). The email log keeps each address-and-link pair to one email, so pressing the button again only sends what is missing. A replaced link's email says it replaces the earlier one. The fields stay, so one link can be fixed by hand; only fields the admin changes are checked, and an untouched old non-Teams link shows a warning instead of blocking.
- **The lobby rule (owner, 2026-11-06).** Board members always go straight in; everyone else (the student) always waits in the lobby until a board member admits them. Board members sign in to Teams with their BTX accounts. Every meeting is set to `lobbyBypassSettings { scope: 'organization', isDialInBypassEnabled: false }` and `allowedPresenters: 'organization'`, never `everyone`. A meeting whose settings cannot be confirmed is not used.
- **How it signs in** (`lib/teams/`, server only): Microsoft Graph as a public client (Microsoft Graph Command Line Tools, no secret), tenant `78915995-e897-47de-b801-0d0dea583962`, scope `OnlineMeetings.ReadWrite User.Read offline_access`, as the organizer account **meetings@btxfoundation.onmicrosoft.com** (a licensed, non-admin user that never attends). Meetings are made with `createOrGet` keyed by the booking (`slotId:applicationId`), so pressing the button again never makes a duplicate, and a slot re-booked by another student gets its own meeting. The title is "BTX scholarship interview" plus the applicant's code, never a name or email.
- **Where the sign-in lives.** Microsoft hands back a new refresh token every time one is used. The newest is kept encrypted in Supabase Vault (secret `btx_teams_refresh_token`), reached only through `public.teams_token_get()` and `public.teams_token_set()`, which only the service role may run (migration `20261106120000_teams_token_vault.sql`). So the feature also needs `SUPABASE_SERVICE_ROLE_KEY`. The daily prep cron (`/api/cron/interview-emails?kind=prep`) uses the token once whenever it is older than about 25 days, so it never lapses between semesters; a failure there is logged as `[teams] token refresh failed` with no detail and changes nothing else.
- **Env var `BTX_TEAMS_REFRESH_TOKEN`** (server only, never `NEXT_PUBLIC_`): the seed, a refresh token for **meetings@**, never the admin account. It is used when nothing is saved yet, and as a fallback when Microsoft refuses the saved token. The saved Vault token is always tried first, so changing the env var alone does **not** replace a saved token that still works; to force a new token, follow "Rotate after a leak" below. With neither a saved token nor the env var (or no service key), the dialog says "Teams isn't connected yet." and the rest of the Ops Hub works as before.
- **Re-seeding.** `python3 -I ~/R&D/platform/teams-meeting.py --org btx login-browser` signs a Microsoft account in on the Mac; for the server, sign in as meetings@ (not admin@) and use that sign-in's own refresh token. Put it into `BTX_TEAMS_REFRESH_TOKEN` on Vercel (an env change, so it is gated like any other), then redeploy. Tokens are never logged, shown or committed.
- **Rotate after a leak** (the refresh token was exposed, or meetings@ may be compromised). In this order:
  1. Microsoft Entra admin center > Users > meetings@btxfoundation.onmicrosoft.com > **Revoke sessions**. This kills every refresh token for the account, the leaked one and the saved one.
  2. Delete the saved token in the BTX Supabase project's SQL editor (a production database change, gated like any other): `delete from vault.secrets where name = 'btx_teams_refresh_token';`
  3. Sign in as meetings@ again to get a new refresh token, put it in `BTX_TEAMS_REFRESH_TOKEN` on Vercel (an env change, gated), and redeploy. The first "Make Teams links" run then saves it to Vault.
- **Deploy order.** Apply the migration **before** the code that uses it goes live. If the code runs first, the token functions don't exist yet and the button says "Couldn't reach Teams. Try again.", which wrongly sounds like a Microsoft outage; the real cause is the missing migration.
- **Time limit.** The Today and Interviews pages export `maxDuration = 300`: Server Actions run under the page that calls them, and a full cycle can take minutes (btx-ops has Fluid compute on).
